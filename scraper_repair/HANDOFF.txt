== WHAT THE PATCH CHANGES ==
(b) Both-teams rule removed. relevant() queues every non-forfeit listed result. --top is optional
    (default 0 for update, watch, results and backfill). With --top N, a match qualifies when EITHER
    team is tracked (TrackedTeams), compared by HLTV team id. A listing row's names map to ids
    through an exact, case-insensitive match against the rankings snapshot and the teams table,
    never fuzzy. All callers are switched over: update, watch (including just-finished live matches),
    the Failsafe listings, the stored-ranking fallback (_stored_tracked) and cmd_results.
    watch.yml passes --top 0 explicitly (scan and backfill_pages step), and so does
    docker-compose. A test fails if any workflow passes --top other than 0 or the top input.
(e) A listing never stops silently. A failed page (or the catch-up cap) raises ListingIncomplete,
    which carries the matches found so far, and saves scraper_state
    'listing_cursor:<source>:<start>:<end>' (next_page, error, since). A range walk resumes one page
    before that point. The scan's catch-up must read past the saved page, and it gets 10 more pages
    each cycle. Catch-up now stops only on a page with nothing unseen: every non-forfeit row is
    stored, queued or already in the manifest. Health check listing_incomplete is an ERROR once the
    scan's listing has been incomplete for more than 6 h. `update` exits 3 when its listing stopped
    early. A dated `update` against the live tables is refused unless --live-history is passed.
(c) Staged revisions (hltv_scraper/revisions.py, CLI `revision create|list|status|accept|seal|
    promote|discard`):
    - create: registers the revision in hltv_meta.dataset_revisions and builds schema hltv_rev_<n>
      with the scraper's own schema.sql. It then copies public into it: foreign keys are dropped for
      the copy and put back NOT VALID, key clashes are counted, and raw_pages/HTML are copied only
      with --seed-archives. Copied rows keep created_revision_id NULL. It also stores a per-match
      fingerprint of every public match older than 3 days (hltv_meta.base_match_fingerprints).
      Writes go only to hltv_meta and the new schema.
    - --revision N (or HLTV_REVISION=N): SET search_path TO hltv_rev_N, with no public fallback. A
      table missing there is an error, never a write to public. Unregistered, discarded or unseeded
      revisions are refused, and the failsafe API is never used.
    - seal: refused while any planned listing is incomplete or any listed match is pending. Stores a
      per-table fingerprint and adds a statement trigger zz_sealed (rejects
      INSERT/UPDATE/DELETE/TRUNCATE) to every table. The registry row is frozen by a trigger, except
      for recording a promotion.
    - promote N --confirm hltv_rev_N --approved-by NAME: sealed revisions only, and only once. It
      runs init_schema on public, locks public.match_overview, and copies in one transaction the
      revision's matches that public lacks (all match-keyed tables). It also copies scrape_queue rows
      public lacks, plus teams, players, maps, events and rankings with ON CONFLICT DO NOTHING.
      Nothing already in public changes. The promoted rows keep created_revision_id = N.
(d) Board scope: `backfill` plans the global listing for the window plus the own listing of each
    board team and opponent (prop_lines.team/opponent, upcoming_matches.team1/team2), each board
    player (prop_lines.player, results?player=ID), and each former team (every team those players
    played for in the window). Matching is by exact name; ambiguous nicknames prefer players whose
    recent team is on the board. Unresolved names are logged; add them with --team-ids / --player-ids
    (workflow input extra_ids). Run it again after the first scrape: former teams found in the new
    matches are added, and the plan only grows. --past-opponents is optional. The default window is
    450 days ending yesterday. A rerun reuses the revision's window, so the cursors stay valid. A
    team or player listing that passes 15 pages is reported incomplete, because that means HLTV
    ignored the filter.
(f) result_manifest (in every schema; append-only, a trigger rejects UPDATE/DELETE/TRUNCATE) logs:
    discovered (once per match and source: teams, team ids when shown, event, played_at from the
    row's timestamp, source URL and page), present, skipped (forfeit, or filtered by --top), stored,
    waiting, unavailable and failed (attempt number and error). The view result_manifest_state gives
    one state per match; discovered = stored + skipped + unavailable + failed + pending. A match
    still without statistics 7 days after it was played, on two looks, becomes 'unavailable' (final,
    counted apart from failures). scrape_queue gets played_at and waits.
(g) raw_pages and mapstats_pages get first_fetched_at: default now() for new rows, NULL (unknown)
    for older rows rather than an invented time, and trigger keep_first_fetched_at rejects any change.
    fetched_at stays the latest fetch; raw_pages also gets refetched_at.
(h) dataset_revisions has revision_id, schema, job, base_schema, started_at, seeded_at, finished_at,
    git_commit, args, counts (seed, base_fingerprint, sealed), complete, promoted_at/by,
    discarded_at and notes. These stat tables get created_revision_id (column default
    current_revision_id(): the constant N in a revision schema, the optional setting
    hltv.revision_id elsewhere) and updated_revision_id (BEFORE UPDATE trigger): match_overview,
    matches, match_maps, player_stats, map_player_stats, map_headshots, map_vetoes, map_rounds,
    map_round_economy, raw_pages and mapstats_pages. A sealed schema cannot change, so each revision
    can be replayed.
backfill.yml is rewritten for staged revisions. Jobs: prepare (create the revision or continue one),
list, scrape (matrix), expand (round 2), scrape2 (matrix), mapstats (matrix), and report (revision
status plus `revision accept`; the job fails until both pass). It never seals or promotes and runs in
its own concurrency group, so the live scan keeps running.

validate.py, new revisions.py and acceptance.py, backfill.yml, watch.yml, docker-compose.yml,

== ACCEPTANCE TESTS ==
`hltv-scraper revision accept N` checks A1-A8. scripts/acceptance_staged.sql has the same checks for
psql, except that A6 there is only the leak check.
  A1 listing completeness: every planned listing (global, team:*, player:*) has a complete cursor,
     and no incomplete cursor remains.
  A2 manifest accounting: discovered = stored + skipped + unavailable + failed + pending, and
     pending = 0.
  A3 coverage against the eligible HLTV listing. Eligible = listed, not a forfeit, played more than
     48 h ago, statistics published (unavailable excluded). Targets: stored/eligible >= 0.99; played
     maps with player stats >= 0.99; with headshots >= 0.98; unavailable <= 2% of listed
     non-forfeit matches. A month table is printed too.
  A4 per board team: the team's own HLTV listing is the denominator. Target stored/eligible >= 0.98,
     or at most 1 missing. Every team is listed.
  A5 timestamps: both triggers present; revision rows have first_fetched_at; first <= latest; a
     change to first_fetched_at is rejected (rolled-back probe).
  A6 public untouched: every public match older than the seed cut-off still has its seed
     fingerprint. Changes the live scan made itself (public.scrape_queue.updated_at >= seeded_at)
     are listed apart. No revision-created match is in public without a live queue row or with
     created_revision_id = N.
  A7 revision ids: stat rows are NULL (copied) or N, nothing else, and every match the revision
     stored carries N.
  A8 (sealed): every table still matches its seal fingerprint, and every table has zz_sealed.
  The BO3.gg cross-checks (R7 c-f) remain CS2 Scout's side.

== CAVEATS ==
- The PostgreSQL tests have not been run (no Postgres here). Treat a red tests.yml as blocking.
- results?team= / results?player= are assumed to be HLTV's listing filters (step 2 checks them). The
  15-page cap keeps an ignored filter from crawling the whole listing once per player.
- Prop team/player names that do not exactly match HLTV names stay unresolved. CS2 Scout's exact
  team-name variants should supply the HLTV ids (extra_ids). Nothing is matched fuzzily.
- The board scope comes from the prop_lines/upcoming_matches copied when the revision was created.
- public rows stored before this patch keep first_fetched_at NULL (unknown), not a reconstructed
  time.
